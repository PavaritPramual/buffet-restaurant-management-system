## Price and payment path

1. [`DiningSession.java:43`](../../code/backend/src/main/java/com/buffetrestaurant/domain/DiningSession.java#L43) stores `package_price_at_open` when a session starts. [`DatabaseDiningSessionBillingReader.java`](../../code/backend/src/main/java/com/buffetrestaurant/service/impl/DatabaseDiningSessionBillingReader.java) reads the session snapshot, and [`DatabaseBillingContextProvider.java:25`](../../code/backend/src/main/java/com/buffetrestaurant/service/impl/DatabaseBillingContextProvider.java#L25) validates the requested ID, snapshot price, guest counts, and status. The browser submits a session ID, not a price or a discount. The current database provider sets `discountContext=null`; percentage discount is supported by the engine but is **not currently supplied by production**.
2. [`BillingConfig.java:16`](../../code/backend/src/main/java/com/buffetrestaurant/config/BillingConfig.java#L16) composes `StandardBillCalculation` with a 0.5 child-rate strategy and `PromotionDiscountStrategy`. [`StandardBillCalculation.java:43`](../../code/backend/src/main/java/com/buffetrestaurant/service/billing/StandardBillCalculation.java#L43) calculates adult price × adults plus child price × child rate × children. Strategy objects keep only immutable policy, while each request's package price and guest counts stay in `BillingContext`; concurrent requests cannot overwrite a previous bill in shared Strategy fields.
3. [`PromotionDiscountStrategy.java:9`](../../code/backend/src/main/java/com/buffetrestaurant/service/billing/PromotionDiscountStrategy.java#L9) accepts a backend-owned percentage from 0 through 100 when present. [`BillingEngine.java:21`](../../code/backend/src/main/java/com/buffetrestaurant/service/billing/BillingEngine.java#L21) rejects invalid policy results, calculates subtotal and reduction with `BigDecimal` at full precision, then rounds **the payable total once** to two decimals using `HALF_UP`. [`BillCalculation.java:6`](../../code/backend/src/main/java/com/buffetrestaurant/service/billing/BillCalculation.java#L6) keeps the precise intermediate values internal. [`BillingPreviewService.java:36`](../../code/backend/src/main/java/com/buffetrestaurant/service/billing/BillingPreviewService.java#L36) makes the displayed discount equal displayed subtotal minus final payable amount, so the public breakdown reconciles. Payment uses that same final amount.
4. [`BillingController.java:31`](../../code/backend/src/main/java/com/buffetrestaurant/controller/BillingController.java#L31) previews without writing a payment. [`PaymentServiceImpl.java:71`](../../code/backend/src/main/java/com/buffetrestaurant/service/impl/PaymentServiceImpl.java#L71) requires authorized Service Staff, a locked `ACTIVE` session, a prior bill request, matching backend context, and no existing payment. It calculates the amount on the server, records `PAID` with `paid_at`, and returns [`PaymentResult`](../../code/backend/src/main/java/com/buffetrestaurant/dto/response/PaymentResult.java). CASH/QR/CARD are **status recording**, not gateway settlement.
5. [`DatabasePaymentStatusLookup.java:24`](../../code/backend/src/main/java/com/buffetrestaurant/service/impl/DatabasePaymentStatusLookup.java#L24) exposes only session ID and status to the session module. [`DiningSessionServiceImpl.java:145`](../../code/backend/src/main/java/com/buffetrestaurant/service/impl/DiningSessionServiceImpl.java#L145) closes only an `ACTIVE` session with a matching `PAID` record; it separately revokes customer grants and frees the table. Paying does not close the table automatically.

| S — one reason to change per component | Billing policy/rounding, preview HTTP flow, payment transaction, and session close rule live in separate components. ## Payment JPA and SQL rationale

[`Payment.java:9`](../../code/backend/src/main/java/com/buffetrestaurant/domain/Payment.java#L9) maps one row to `payments`, with a generated ID, `DECIMAL(10,2)` amount, string method/status enums, and nullable `OffsetDateTime paidAt`. The entity stores `sessionId` as a plain `Long`, **not** a JPA `@OneToOne` or `@ManyToOne`. Therefore it has no JPA fetch mode, no association cascade, and no inverse collection on `DiningSession`. [`PaymentRepository.java:12`](../../code/backend/src/main/java/com/buffetrestaurant/repository/PaymentRepository.java#L12) performs the lookup by session ID; no lazy association is dereferenced when producing the response.

The database still enforces the relationship: [`V9__create_payments_table.sql:3`](../../code/backend/src/main/resources/db/migration/postgresql/V9__create_payments_table.sql#L3) makes `session_id` unique and the FK uses `ON DELETE RESTRICT`. That prevents two payment rows for one session and prevents deleting a session with payment history. The service's existence check gives a clear 409 before insert; the database uniqueness constraint is the final concurrency backstop. The service locks the session row before checking and recording, coordinating with order, bill request, and close. SQL CHECK constraints restrict amount/method/status and require `paid_at` only for `PAID`. [`V12__align_payment_backend_privileges.sql`](../../code/backend/src/main/resources/db/migration/postgresql/V12__align_payment_backend_privileges.sql) grants access to the backend DB role while restricting client roles. Tests use a separate H2/PostgreSQL database, not the shared Supabase project.
